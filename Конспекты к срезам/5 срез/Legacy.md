
# 🔴  Тема: Работа с legacy 🔴 

**На двойку: Что такое legacy система**

**Legacy-система** — существующая устаревшая система, которая продолжает использоваться бизнесом, но её сложно изменять, сопровождать или развивать.

Важно:
- legacy ≠ обязательно плохая или старая система;
- она может быть критична для бизнеса;
- часто отсутствует документация;
- знания могут находиться только у отдельных специалистов;
- изменение одного компонента может повлиять на множество других.

> Главная проблема legacy — **высокая стоимость и риск изменений**, а не просто возраст системы.

---

🧐 **на тройку: Как правильно интегрироваться с legacy**

### Strangler Fig Pattern

**Strangler Fig** — постепенная замена legacy-системы новой системой.

Идея:

```text
Сначала:

Client → Legacy

Постепенно:

Client → New System → Legacy
              ↓
         новые функции

В конце:

Client → New System
````

Новая система постепенно перехватывает функциональность старой, пока legacy не становится ненужной.

**Плюс:** не нужно переписывать всю систему сразу.

---

### ACL — Anti-Corruption Layer

**ACL** — промежуточный слой между новой и legacy-системой, который преобразует модели и протоколы между ними.

```
New System
    ↓
   ACL
    ↓
Legacy System
```

Например:

```
Новая модель Customer
        ↓
      ACL
        ↓
Старая модель Client
```

ACL защищает новую систему от:

- устаревшей модели данных;
- странных форматов;
- legacy-бизнес-логики;
- технических ограничений старой системы.

> Новая система не должна «заражаться» legacy-моделью.

---

### Событийная интеграция (Event-Driven)

Legacy может публиковать события:

```
Legacy
  ↓
Event Broker
  ↓
New System
```

Например:

```
CustomerCreated
OrderCreated
PaymentCompleted
```

Новая система подписывается на необходимые события и реагирует на них.

**Плюсы:**

- слабая связанность;
- системы могут развиваться независимо;
- асинхронность;
- можно подключать несколько потребителей.

**Важно учитывать:**

- повторную доставку;
- идемпотентность;
- порядок событий;
- потерю событий;
- eventual consistency.

---

### Файловый обмен как крайний шаг

Если legacy не предоставляет API или событийную интеграцию, можно использовать файлы:

```
Legacy
   ↓
CSV / XML / JSON
   ↓
SFTP / файловое хранилище
   ↓
New System
```

**Минусы:**

- задержка;
- сложнее контроль ошибок;
- возможны дубли;
- сложнее обеспечить актуальность данных;
- сложнее мониторинг.

Используется, когда более современные способы интеграции невозможны или слишком дороги.

---

😎 **на четверку: На что стоит обращать внимание, чтобы ничего не сломать?**

При интеграции с legacy главное — **не менять существующее поведение без понимания его влияния**.

### 1. Контракт интеграции

Нужно понять:

- какие API / интерфейсы существуют;
- формат запросов и ответов;
- обязательные поля;
- коды ошибок;
- таймауты;
- ограничения;
- обратную совместимость.

> Не менять контракт без анализа всех потребителей.

### 2. Скрытая бизнес-логика

В legacy может быть логика, которой нет в документации.

Нужно выяснить:

- какие проверки выполняются;
- какие поля обязательны фактически;
- какие есть неочевидные зависимости;
- какие side effects возникают при вызове.

### 3. Зависимости

Проверить:

```
Кто вызывает legacy?
Кого вызывает legacy?
Какие БД использует?
Какие очереди / файлы / сервисы?
Какие batch-процессы?
```

### 4. Данные

Особенно внимательно проверить:

- форматы;
- кодировки;
- `NULL`;
- значения по умолчанию;
- справочники;
- идентификаторы;
- даты и часовые пояса;
- дубли;
- исторические данные.

### 5. Производительность и нагрузка

Новая интеграция может увеличить нагрузку на legacy.

Проверить:

- RPS;
- лимиты;
- timeout;
- connection pool;
- время ответа;
- пиковую нагрузку.

Не стоит делать:

```
New System
   ↓
1000 синхронных запросов
   ↓
Legacy
```

если legacy рассчитана на значительно меньшую нагрузку.

### 6. Ошибки и отказоустойчивость

Нужно предусмотреть:

- timeout;
- retry;
- circuit breaker;
- недоступность legacy;
- частичный успех;
- дублирование запросов;
- идемпотентность.

Особенно важно осторожно использовать **retry** для операций, которые изменяют данные.

### 7. Постепенное внедрение

Лучше:

```
Новая интеграция
      ↓
Тестирование
      ↓
Canary / небольшой процент
      ↓
Мониторинг
      ↓
Постепенное увеличение
```

а не сразу переключать весь трафик.

### 8. Rollback

До запуска должно быть понятно:

> **Как вернуть систему в предыдущее состояние, если новая интеграция сломает legacy?**

Нужны:

- feature toggle;
- возможность быстро отключить новую интеграцию;
- rollback;
- мониторинг;
- алерты.

### 9. Мониторинг

После изменений отслеживать:

- ошибки;
- latency;
- RPS;
- timeout;
- нагрузку на legacy;
- количество успешных/неуспешных операций;
- бизнес-метрики.

> **Главное правило при работе с legacy: сначала понять существующее поведение и зависимости, затем изолировать legacy, делать изменения постепенно и обязательно иметь мониторинг + rollback.**
