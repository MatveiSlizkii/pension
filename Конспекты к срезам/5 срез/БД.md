## 🧐 на тройку: Определение СУБД. Функции СУБД. Типы СУБД. 

**Определение СУБД** — программное обеспечение для создания, хранения, изменения, удаления и получения данных в БД, а также управления доступом к ним.

**Функции СУБД:**

- хранение и управление данными;
- выполнение запросов;
- добавление / изменение / удаление данных;
- управление транзакциями;
- обеспечение целостности данных;
- управление доступом и правами;
- резервное копирование и восстановление;
- многопользовательский доступ и конкурентная работа.

**Типы СУБД:**

- **реляционные (SQL)** — данные в таблицах, связи между таблицами;
- **документные (NoSQL)** — данные в виде документов;
- **ключ-значение** — значение доступно по уникальному ключу;
- **колоночные** — данные организованы по колонкам, эффективны для аналитики;
- **графовые** — данные представлены вершинами и связями;
- **временные (Time-Series)** — оптимизированы для данных, привязанных ко времени.

## 😎на четверку: Сравнение различных типов баз данных с приведением разных типов и классификаций с приведением конкретных приверов БД или СУБД

**Реляционные (SQL):** PostgreSQL, MySQL, Oracle  
**Документные (NoSQL):** MongoDB, CouchDB  
**Ключ-значение:** Redis, Memcached  
**Колоночные:** Cassandra, HBase  
**Графовые:** Neo4j, ArangoDB  
**Временные (Time-Series):** InfluxDB, TimescaleDB


**Кратко чем хорош каждый тип:**

- **Реляционные (SQL):** строгая структура, связи между таблицами, ACID-транзакции, сложные запросы. Хороши для банковских/бизнес-систем.
- **Документные (NoSQL):** гибкая структура документов, удобно хранить сложные/вложенные объекты, легко изменять схему.
- **Ключ-значение:** очень быстрый доступ по ключу. Хороши для кэшей, сессий, счётчиков, временных данных.
- **Колоночные:** высокая производительность на больших объёмах данных и при распределённом хранении; хорошо для аналитики и больших потоков данных.
- **Графовые:** эффективны для данных, где важны **связи между объектами** — социальные сети, рекомендации, зависимости.
- **Временные (Time-Series):** оптимизированы для данных с временной шкалой — метрики, логи, мониторинг, цены, показания датчиков.

## 🥉На двойку: Определение логической и физической моделей баз данных. ERD. Типы данных.**

**Логическая модель БД** — описание структуры данных и связей между ними без привязки к конкретной СУБД.

Содержит:
- сущности / таблицы;
- атрибуты / поля;
- первичные и внешние ключи;
- связи между сущностями;
- ограничения.

**Физическая модель БД** — описание конкретной реализации логической модели в определённой СУБД.

Содержит:
- конкретные типы данных;
- индексы;
- constraints;
- партиционирование;
- sequence / identity;
- особенности хранения.

> Логическая модель — **что и как связано**.  
> Физическая модель — **как это конкретно реализовано**.

**ERD (Entity Relationship Diagram)** — диаграмма сущностей и связей между ними.

Показывает:
- сущности;
- атрибуты;
- связи;
- кардинальность: `1:1`, `1:N`, `M:N`.

**Типы данных** — определяют, какие значения может хранить поле.

- `INTEGER / BIGINT` — целые числа;
- `DECIMAL / NUMERIC` — точные числа, например деньги;
- `VARCHAR / TEXT` — строки;
- `BOOLEAN` — true / false;
- `DATE` — дата;
- `TIMESTAMP` — дата и время;
- `JSON / JSONB` — JSON-структуры;
- `UUID` — уникальный идентификатор.

## 🧐 **на тройку: Нормализация и денормализация.**

**Нормализация** — приведение структуры БД к виду, при котором уменьшается избыточность данных и вероятность аномалий.

**1НФ:**

- значения должны быть атомарными;
- нет повторяющихся групп.

**2НФ:**

- БД находится в 1НФ;
- каждый неключевой атрибут зависит от всего составного ключа, а не от его части.

**3НФ:**

- БД находится во 2НФ;
- нет зависимости неключевого атрибута от другого неключевого атрибута.

**Зачем нормализуют:**

- уменьшить дублирование;
- избежать противоречий в данных;
- упростить изменение данных;
- повысить целостность.

**Денормализация** — намеренное добавление избыточности в БД ради производительности или упрощения чтения.

**Плюсы:**

- меньше `JOIN`;
- быстрее чтение;
- удобно для read-heavy систем и аналитики.

**Минусы:**

- дублирование данных;
- больше занимаемого места;
- сложнее обновление;
- риск рассинхронизации данных.

> **Нормализация** — уменьшаем избыточность и повышаем целостность.  
> **Денормализация** — сознательно добавляем избыточность ради производительности.

## 😎а четверку: Понятие индексов в базах данных и их назначение.**

**Индекс** — специальная структура данных, которая позволяет СУБД быстрее находить записи по определённым значениям.

> Аналогия: индекс в БД ≈ алфавитный указатель в книге.

Без индекса СУБД может выполнить **Full Table Scan** — последовательно проверить строки таблицы.

Пример:

```
CREATE INDEX idx_users_email
ON users(email);
```

После этого поиск:

```
SELECT *
FROM users
WHERE email = 'a@test.com';
```

может выполняться значительно быстрее.

**Индексы полезны для:**

- `WHERE`;
- `JOIN`;
- `ORDER BY`;
- иногда `GROUP BY`;
- поиска по диапазонам.

**Цена индексов:**

- занимают дополнительное место;
- замедляют `INSERT`;
- замедляют `UPDATE`;
- замедляют `DELETE`;
- требуют обслуживания.

Поэтому индексировать все поля подряд — плохая практика.

**Основные виды:**

**B-tree** — наиболее распространённый тип. Подходит для:

- `=`;
- `>`;
- `<`;
- `>=`;
- `<=`;
- `BETWEEN`;
- `ORDER BY`.

**Hash** — эффективен в основном для поиска по точному совпадению.

**Составной индекс** — индекс по нескольким колонкам:

```
CREATE INDEX idx_user_status_date
ON users(status, created_at);
```

Важен порядок колонок — работает принцип **левого префикса**.

Для индекса `(status, created_at)` эффективно использовать:

- `status`;
- `status + created_at`.

Но индекс не обязательно эффективно используется для поиска только по `created_at`.

**Как понять, нужен ли индекс:**

1. Посмотреть реальные запросы.
2. Определить поля из `WHERE`, `JOIN`, `ORDER BY`.
3. Посмотреть план выполнения через `EXPLAIN / EXPLAIN ANALYZE`.
4. Создать индекс.
5. Сравнить производительность.
6. Проверить влияние на `INSERT / UPDATE / DELETE`.


# 🔴 Тема: ACID. Транзакции 🔴

## 🥉На двойку: Понятие ACID**

**ACID** — набор свойств транзакций, обеспечивающий надёжность и предсказуемость работы с данными.

**A — Atomicity (Атомарность)**
- Транзакция выполняется целиком или не выполняется вообще.
- При ошибке изменения откатываются (`ROLLBACK`).

**C — Consistency (Согласованность)**
- После успешной транзакции БД остаётся в корректном состоянии.
- Соблюдаются ограничения, связи, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK` и т.д.

**I — Isolation (Изолированность)**
- Параллельные транзакции не должны некорректно влиять друг на друга.
- Результат зависит от уровня изоляции.

**D — Durability (Надёжность)**
- После `COMMIT` изменения сохраняются даже при сбое/перезапуске БД.
- Обеспечивается механизмами журналирования и восстановления.

> **A** — всё или ничего.  
> **C** — БД остаётся корректной.  
> **I** — параллельные транзакции изолированы.  
> **D** — `COMMIT` не теряется.

---

## 🧐 **на тройку: Понятие Транзакции**

**Транзакция** — логически единая последовательность операций над БД, которая выполняется как единое целое.

Основные команды:
- `BEGIN` — начало транзакции;
- `COMMIT` — подтвердить изменения;
- `ROLLBACK` — отменить изменения.

Обе операции должны выполниться успешно.

Если вторая операция завершилась ошибкой:

→ первая операция также отменяется.

**Зачем нужны транзакции:**
- сохранить целостность данных;
- выполнить несколько операций как единое целое;
- обеспечить корректную работу при ошибках;
- контролировать параллельный доступ.

---

## 😎 **на четверку: Привести примеры транзакций и привести примеры, когда транзакция может не пройти**

**Пример 1 — перевод денег**

```
1. Списать деньги со счёта A.
2. Зачислить деньги на счёт B.
3. COMMIT.
```

Если зачисление на B не удалось → `ROLLBACK`, деньги на A возвращаются.

**Пример 2 — создание заказа**

```
1. Создать заказ.
2. Создать позиции заказа.
3. Уменьшить остаток товара.
4. COMMIT.
```

Если одна из операций не выполнена → откатываем всю транзакцию.

**Пример 3 — регистрация пользователя**

```
1. Создать пользователя.
2. Создать его профиль.
3. Создать настройки.
4. COMMIT.
```

Если создание профиля не удалось → пользователь не должен остаться созданным без необходимых данных.

### Когда транзакция может не пройти

**1. Нарушение ограничений БД**

- `PRIMARY KEY` — попытка создать дубликат;
- `UNIQUE` — значение уже существует;
- `FOREIGN KEY` — ссылка на несуществующую запись;
- `CHECK` — значение не соответствует условию;
- `NOT NULL` — передали `NULL`.

**2. Конфликт параллельных транзакций**

- блокировка;
- `deadlock`;
- serialization failure при высоком уровне изоляции.

Например:

```
T1 блокирует A → пытается получить B
T2 блокирует B → пытается получить A
```

→ возникает `deadlock`.

**3. Ошибка приложения**

- SQL-запрос сформирован неправильно;
- нарушена бизнес-логика;
- приложение явно вызвало `ROLLBACK`.

**4. Ошибка БД / инфраструктуры**

- потеря соединения;
- падение БД;
- timeout;
- нехватка ресурсов.

**5. Нарушение бизнес-условий**

Например:

```
Баланс = 500 ₽
Попытка списать 1000 ₽
```

Если бизнес-правило запрещает отрицательный баланс → операция отклоняется и транзакция откатывается.

> Важно: **не любая ошибка автоматически означает `ROLLBACK`** — поведение зависит от типа ошибки, СУБД и того, как приложение управляет транзакцией.

## 🧐 **на тройку: Привести примеры DDL, DML. Понимание Constraint**

**SQL** — язык для работы с реляционными БД.

### DDL — Data Definition Language

Используется для **создания и изменения структуры БД**.

Основные команды:
- `CREATE` — создание;
- `ALTER` — изменение;
- `DROP` — удаление;
- `TRUNCATE` — удаление всех записей из таблицы без удаления самой таблицы.
### DML — Data Manipulation Language

Используется для **работы с данными внутри таблиц**.

Основные команды:

- `SELECT` — получение;
- `INSERT` — добавление;
- `UPDATE` — изменение;
- `DELETE` — удаление.
### DCL — Data Control Language

Управление **правами доступа**.

- `GRANT` — выдать права;
- `REVOKE` — забрать права.

### TCL — Transaction Control Language

Управление **транзакциями**.

- `BEGIN`;
- `COMMIT`;
- `ROLLBACK`;
- `SAVEPOINT`.

---

### Constraint

**Constraint** — ограничение, которое задаёт правила допустимых данных в таблице и обеспечивает целостность данных.

Основные:

**PRIMARY KEY**

- уникально идентифицирует запись;
- `UNIQUE + NOT NULL`;
- на него автоматически создаётся уникальный индекс.



**FOREIGN KEY**

- обеспечивает ссылочную целостность;
- связывает запись с записью в другой таблице.

**UNIQUE**

- запрещает дублирование значения.

**NOT NULL**

- запрещает `NULL`.

**CHECK**

- задаёт условие для значения.

**DEFAULT**

- задаёт значение по умолчанию.

> Constraint позволяет перенести часть правил целостности данных непосредственно в БД, а не контролировать их только на уровне приложения.

Агрегатная функция

**Агрегатная функция** выполняет вычисление над набором строк и возвращает **одно значение**
Основные:

- `COUNT()` — количество;
- `SUM()` — сумма;
- `AVG()` — среднее;
- `MIN()` — минимум;
- `MAX()` — максимум.

---

### Оконная функция

**Оконная функция** выполняет вычисление по набору связанных строк, но **не схлопывает строки в одну**, как `GROUP BY`.

Основные:

- `ROW_NUMBER()`;
- `RANK()`;
- `DENSE_RANK()`;
- `LAG()`;
- `LEAD()`;
- `SUM() OVER`;
- `AVG() OVER`.

Пример:

```
SELECT
    customer_id,
    balance,
    SUM(balance) OVER (PARTITION BY customer_id) AS total_balance
FROM accounts;
```

В результате каждая исходная строка сохраняется, но дополнительно получает сумму по своему клиенту.

> **GROUP BY** → несколько строк превращаются в одну строку на группу.  
> **Window function** → строки сохраняются, вычисление добавляется к каждой строке.

---

### Процедура vs функция

**Функция**

- возвращает значение;
- может использоваться внутри SQL-запроса;
- обычно применяется для вычислений / преобразований.

**Процедура**

- выполняет последовательность действий;
- может не возвращать значение;
- вызывается отдельной командой `CALL`;
- предназначена скорее для выполнения операций / бизнес-логики на стороне БД.

> Главное отличие: **функция возвращает результат и может использоваться в запросе, процедура выполняет действие и вызывается отдельно.**

---

### GROUP BY vs HAVING

**GROUP BY** — группирует строки по указанным полям.

```
SELECT customer_id, COUNT(*)
FROM orders
GROUP BY customer_id;
```

Получаем количество заказов для каждого клиента.

**HAVING** — фильтрует **уже сформированные группы**.

```
SELECT customer_id, COUNT(*)
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 5;
```

Получаем только клиентов, у которых больше 5 заказов.

> **WHERE** — фильтрует строки **до группировки**.  
> **HAVING** — фильтрует группы **после группировки**.

```
FROM
  ↓
WHERE       ← фильтрация строк
  ↓
GROUP BY    ← группировка
  ↓
HAVING      ← фильтрация групп
  ↓
SELECT
```

### JOIN

**JOIN** используется для объединения данных из нескольких таблиц по связанному условию.

### INNER JOIN

Возвращает только записи, для которых есть совпадение в обеих таблицах.

> Только клиенты, у которых есть заказы.

### LEFT JOIN

Возвращает **все записи из левой таблицы** и совпавшие записи из правой.

Если совпадения нет → поля правой таблицы будут `NULL`.

> Все клиенты, даже если у них нет заказов.

### RIGHT JOIN

Аналог `LEFT JOIN`, но сохраняет **все записи правой таблицы**.

### FULL OUTER JOIN

Возвращает:

- совпавшие записи;
- записи только из левой таблицы;
- записи только из правой таблицы.

Если соответствия нет → с противоположной стороны `NULL`.

### CROSS JOIN

Декартово произведение.

Каждая строка первой таблицы соединяется с каждой строкой второй.

Если:

- таблица A — 3 строки;
- таблица B — 4 строки;

результат = **12 строк**.

# 🔴 Тема: Логирование (ELK) 🔴

## 🥉На двойку: Понятие логирования. Цели логирования. Виды логов.**

**Логирование** — процесс записи информации о событиях, происходящих в системе, для последующего анализа, мониторинга и расследования проблем.

**Цели логирования:**
- поиск и диагностика ошибок;
- мониторинг работы системы;
- анализ действий пользователей;
- расследование инцидентов;
- аудит;
- анализ производительности;
- восстановление хронологии событий.

**Виды логов:**

**По назначению:**
- **Application logs** — работа приложения, бизнес-операции, ошибки.
- **Access logs** — входящие HTTP-запросы и ответы.
- **Error logs** — ошибки и исключения.
- **Audit logs** — действия пользователей и изменения данных.
- **Security logs** — события безопасности, авторизация, доступ.
- **Performance logs** — время выполнения операций, нагрузка.

**По уровню:**
- `TRACE` — максимально подробная информация;
- `DEBUG` — информация для отладки;
- `INFO` — штатные события;
- `WARN` — потенциальная проблема;
- `ERROR` — ошибка операции;
- `FATAL` — критическая ошибка, приводящая к остановке компонента.

> Лог должен отвечать минимум на вопросы: **что произошло, когда, где и с каким результатом**.

---

## 🧐 **на тройку: Инструменты для логирования. Принципы работы инструментов. Примеры работы с логами на практике.**

### ELK

**ELK** — стек для централизованного сбора, обработки, хранения и поиска логов:

- **Elasticsearch** — хранение и быстрый поиск логов;
- **Logstash** — получение, обработка, преобразование и отправка логов;
- **Kibana** — визуализация и анализ логов.

Типичный поток:

```text id="n3d7qa"
Приложение
    ↓
Logstash / Beats / Agent
    ↓

    ↓

````

Также часто используется **Filebeat**:

```
Application
    ↓

    ↓

    ↓

    ↓

```

### Принцип работы

1. Приложение формирует лог.
2. Лог передаётся агенту/сборщику.
3. Лог при необходимости парсится и обогащается.
4. Запись отправляется в Elasticsearch.
5. Kibana позволяет искать, фильтровать и визуализировать данные.
6. На основе логов можно строить dashboards и alerts.

## 😎 **на четверку: Понимание особенности работы с различными инструментами логирования. Как сформировать структуру логов.**

### Особенности инструментов

**Elasticsearch**

- хранит и индексирует логи;
- быстро ищет по полям;
- подходит для больших объёмов данных;
- требует контроля индексов, retention и объёма хранения.

**Logstash**

- получает логи из различных источников;
- парсит и преобразует данные;
- может обогащать события;
- отправляет данные в Elasticsearch или другие хранилища;
- достаточно ресурсоёмкий.

**Filebeat**

- лёгкий агент;
- обычно собирает логи с файлов/источников;
- отправляет их дальше;
- подходит для установки рядом с приложением.

**Kibana**

- поиск и анализ;
- dashboards;
- визуализация;
- фильтрация;
- alerts.

**Loki**

- хранит логи с упором на эффективное хранение и поиск по labels;
- часто используется вместе с Grafana;
- в отличие от Elasticsearch не индексирует весь текст лога целиком.

> При выборе инструмента смотрим на объём логов, требования к поиску, стоимость хранения, производительность и необходимость визуализации.

---

### Как сформировать структуру логов

Лучше использовать **структурированные логи**, например JSON, а не произвольный текст.

Пример:

```
{
  "timestamp": "2026-10-08T12:30:45.123Z",
  "level": "INFO",
  "service": "deposit-v2-api",
  "environment": "prod",
  "traceId": "abc123",
  "requestId": "req456",
  "method": "POST",
  "path": "/deposits",
  "operation": "createDeposit",
  "customerId": "123456",
  "durationMs": 125,
  "statusCode": 200,
  "message": "Deposit successfully created"
}
```

### Минимально полезные поля

- `timestamp` — когда произошло;
- `level` — уровень лога;
- `service` — какой сервис;
- `environment` — окружение;
- `traceId` / `requestId` — идентификатор запроса;
- `operation` — какая операция выполнялась;
- `message` — описание события;
- `durationMs` — длительность;
- `statusCode` — результат HTTP-запроса;
- технические/бизнес-параметры, необходимые для расследования.

### Требования к хорошей структуре

- единый формат логов во всех сервисах;
- понятные и одинаковые названия полей;
- timestamp в едином формате, обычно UTC;
- наличие `traceId` для трассировки запроса;
- значения должны быть пригодны для фильтрации и агрегации;
- не логировать пароли, токены, секреты и лишние персональные данные;
- не писать огромные объекты без необходимости;
- разделять технические и бизнес-события;
- заранее определить уровни логирования.

> Хороший лог должен позволять быстро ответить: **когда произошло → в каком сервисе → какой запрос → какая операция → какой результат → сколько заняло времени → что пошло не так**.



# 🔴 Тема: Типы NoSQL БД. Когда они используются 🔴

## 🥉На двойку: Что такое NoSQL БД**

**NoSQL (Not Only SQL)** — класс баз данных, которые не используют классическую реляционную модель как основной способ хранения данных.

Основные особенности:
- гибкая или динамическая схема;
- горизонтальное масштабирование;
- высокая производительность для определённых типов нагрузки;
- рассчитаны на большие объёмы и/или высокую скорость обработки данных;
- не обязательно используют SQL как основной язык запросов.

**Основные типы NoSQL БД:**

- **Key-Value** — `ключ → значение`. Redis.
- **Document** — документы, обычно JSON/BSON. MongoDB.
- **Column-family / Wide-column** — данные организованы по семействам колонок. Cassandra.
- **Graph** — узлы и связи между ними. Neo4j.

> NoSQL ≠ «БД без SQL». Правильнее понимать как **Not Only SQL** — альтернативные модели хранения данных помимо реляционной.

---

## 🧐 **на тройку: Когда используются NoSQL БД**

NoSQL выбирают, когда реляционная модель плохо подходит под требования системы.

**Основные причины:**
- большой объём данных;
- высокая нагрузка и большое количество операций;
- необходимость горизонтального масштабирования;
- данные имеют гибкую/часто меняющуюся структуру;
- нужно быстро работать с конкретным типом данных;
- требуется высокая доступность;
- данные естественно представляются в виде документов, графа или `key-value`.

**Примеры:**

**Redis**
- кэш;
- сессии;
- временные данные;
- rate limiting;
- очереди / счётчики.

**MongoDB**
- документы с гибкой структурой;
- каталоги товаров;
- профили;
- данные, которые удобно хранить целиком как JSON-документ.

**Cassandra**
- очень большие объёмы данных;
- высокая нагрузка на запись;
- распределённые системы;
- требования к высокой доступности.

**Neo4j**
- сложные связи между объектами;
- социальные графы;
- рекомендации;
- поиск взаимосвязей.

> NoSQL выбирают не потому, что SQL «плохой», а когда конкретные требования системы лучше закрываются другой моделью хранения.

---

## 😎 **на четверку: Может объяснить преимущества и недостатки NoSQL БД. Привести причины использования сочетаний SQL и NoSQL в рамках одного проекта**

### Преимущества NoSQL

- **Горизонтальное масштабирование** — можно добавлять новые узлы.
- **Высокая производительность** для подходящего сценария.
- **Гибкая схема** — проще работать с изменяющейся структурой данных.
- **Высокая доступность** — многие NoSQL БД изначально рассчитаны на распределённую работу.
- Хорошо работают с **большими объёмами данных**.
- Можно подобрать модель хранения под конкретную задачу.

### Недостатки NoSQL

- Не всегда есть полноценные `JOIN`.
- Сложнее обеспечить сложные связи между данными.
- Возможна **денормализация** и дублирование данных.
- Транзакционные возможности могут быть слабее или устроены иначе, чем в SQL.
- Сложнее выполнять сложные аналитические запросы в некоторых системах.
- Требуется хорошо понимать особенности конкретной NoSQL БД.
- Масштабирование и распределённость добавляют архитектурную сложность.

> Нельзя сказать, что NoSQL в целом лучше или хуже SQL — выбор зависит от требований к данным и нагрузке.

---

### Почему используют SQL + NoSQL в одном проекте

Это называется **polyglot persistence** — использование разных типов хранилищ для разных задач.

Например:

```text id="p7m2xq"
                ┌── PostgreSQL
Application ────┤
                └── Redis
````

**PostgreSQL:**

- основные бизнес-данные;
- транзакции;
- связи между сущностями;
- строгая целостность;
- сложные SQL-запросы.

**Redis:**

- кэш часто запрашиваемых данных;
- сессии;
- временные данные;
- быстрые счётчики.

Другой пример:

```
PostgreSQL → источник истины
MongoDB    → хранение документов / read model
Elasticsearch → полнотекстовый поиск
Redis      → кэш
```

### Причины сочетания

- разные требования к разным типам данных;
- оптимизация производительности;
- снижение нагрузки на основную БД;
- кэширование;
- специализированный поиск;
- хранение данных в наиболее подходящей модели;
- возможность масштабировать отдельные компоненты независимо.

**Пример:**

Пользователь открывает каталог товаров:

```
1. PostgreSQL → источник актуальных данных.
2. MongoDB → хранение готовой структуры товара.
3. Redis → кэш популярных товаров.
4. Elasticsearch → поиск по названию и описанию.
```

> **SQL** обычно отвечает за источник истины и транзакционность.  
> **NoSQL** используется для конкретных задач, где важны скорость, масштабирование, гибкая структура или специализированный способ доступа к данным.

**На интервью важно:** если используем несколько БД, нужно учитывать **согласованность данных, синхронизацию, отказоустойчивость и то, какая система является source of truth**.  


# 🔴 Тема: PostgreSQL 🔴

## 🥉На двойку: Что такое PostgreSQL и чем она отличается от других СУБД, например, от MySQL или Oracle?  
Что такое репликация в PostgreSQL?  
Как в PostgreSQL можно управлять правами доступа и ролями пользователей?**

**PostgreSQL** — объектно-реляционная СУБД с открытым исходным кодом, ориентированная на надёжность, расширяемость и работу со сложными структурами данных.

**Особенности PostgreSQL:**
- полноценная поддержка SQL;
- ACID-транзакции;
- сложные запросы и `JOIN`;
- мощная система индексов;
- `JSON / JSONB`;
- оконные функции;
- CTE;
- пользовательские типы данных;
- расширения;
- развитая система ограничений и целостности.

**Отличия от MySQL:**
- PostgreSQL обычно предоставляет более широкий набор SQL-возможностей;
- сильная поддержка сложных запросов и типов данных;
- развитая расширяемость;
- PostgreSQL часто выбирают для сложных бизнес-систем и аналитических запросов.

**Отличия от Oracle:**
- PostgreSQL — open source и не требует коммерческой лицензии;
- Oracle имеет более широкий набор корпоративных возможностей и собственных технологий;
- синтаксис и некоторые механизмы работы отличаются;
- PostgreSQL часто используется как более доступная альтернатива Oracle.

---

### Репликация в PostgreSQL

**Репликация** — копирование данных с одного экземпляра PostgreSQL на другой.

Основные роли:

```text id="8j4kqp"
Primary
   │
   ├── WAL ──→ Replica
   │
   └── WAL ──→ Replica
````

**Primary** — принимает операции записи.

**Replica / Standby** — получает изменения и обычно используется для чтения или отказоустойчивости.

**Зачем нужна:**

- отказоустойчивость;
- резервирование;
- масштабирование чтения;
- возможность переключения на резервный сервер.

Основной механизм — передача **WAL (Write-Ahead Log)** от primary к standby.

---

### Управление правами и ролями

В PostgreSQL используется система **roles**.

Роль может использоваться как пользователь или как группа.

Основные команды:

**GRANT** — выдаёт права.

**REVOKE** — отзывает права.

Можно создавать роли-группы и выдавать права группе, а пользователей добавлять в неё.

Основные права:

- `SELECT`;
- `INSERT`;
- `UPDATE`;
- `DELETE`;
- `EXECUTE`;
- `USAGE`;
- `CREATE` и др.

> Хорошая практика — выдавать минимально необходимые права (**principle of least privilege**).

## 🧐 **на тройку: Что такое индексы и для чего они используются в PostgreSQL? Какие типы индексов существуют?  
Как работает система транзакций в PostgreSQL? Что такое ACID?  
Что такое EXPLAIN и как его можно использовать для оптимизации запросов в PostgreSQL?**

### Индексы

**Индекс** — дополнительная структура данных, позволяющая быстрее находить записи по определённым значениям.

Пример:

```
CREATE INDEX idx_users_email
ON users(email);
```

Без индекса PostgreSQL может выполнить `Seq Scan` — последовательное чтение таблицы.

С индексом может использовать `Index Scan` / `Bitmap Index Scan`.

**Основные типы индексов PostgreSQL:**

- **B-tree** — основной и наиболее распространённый;
- **Hash** — поиск по точному равенству;
- **GIN** — эффективно работает с массивами, `JSONB`, полнотекстовым поиском;
- **GiST** — специализированные типы данных, геоданные, диапазоны;
- **SP-GiST** — специализированные структуры данных;
- **BRIN** — эффективен для очень больших таблиц, когда значения физически коррелируют с порядком строк.

**Важно:**

- `PRIMARY KEY` → автоматически создаётся уникальный индекс;
- `UNIQUE` → автоматически создаётся уникальный индекс;
- `FOREIGN KEY` → автоматически индекс **не создаётся**.

> Индекс ускоряет чтение, но занимает место и замедляет операции изменения данных.

---

### Транзакции в PostgreSQL

**Транзакция** — набор операций, выполняемый как единое логическое целое.

```
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

При ошибке:

```
ROLLBACK;
```

→ изменения транзакции отменяются.

PostgreSQL использует **MVCC (Multi-Version Concurrency Control)** для работы с параллельными транзакциями.

Идея:

> Читающие транзакции обычно не блокируют пишущие и наоборот; PostgreSQL работает с версиями строк.

### ACID

- **Atomicity** — всё или ничего.
- **Consistency** — данные остаются корректными.
- **Isolation** — параллельные транзакции изолированы согласно уровню изоляции.
- **Durability** — после `COMMIT` изменения сохраняются.

---

### EXPLAIN

**EXPLAIN** показывает план, который PostgreSQL собирается использовать для выполнения SQL-запроса.

```
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@test.com';
```

Для фактического выполнения:

```
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@test.com';
```

Смотрим:

- тип сканирования: `Seq Scan`, `Index Scan`, `Bitmap Scan`;
- количество строк;
- стоимость (`cost`);
- фактическое время;
- количество фактически обработанных строк;
- `loops`;
- где происходит основная нагрузка.

Пример:

```
Seq Scan
↓
Понимаем, что читается вся таблица
↓
Проверяем фильтр / индекс
↓
Создаём или изменяем индекс
↓
Повторяем EXPLAIN ANALYZE
↓
Сравниваем план
```

> `EXPLAIN` — инструмент анализа плана выполнения, а не просто «проверка скорости запроса».

- `SMALLINT`;
- `INTEGER`;

- `NUMERIC / DECIMAL`;
- `REAL`;

**Строковые:**

**Дата и время:**

- `DATE`;

- `TIMESTAMPTZ`;

---

### JSON и JSONB

Оба типа позволяют хранить JSON-данные:

```
{
  "name": "Ivan",
  "age": 30
}
```

**JSON**

- хранит JSON в исходном текстовом представлении;
- сохраняет исходный формат;
- при чтении требуется разбор JSON.

**JSONB**

- хранит данные в бинарном разобранном виде;
- быстрее работает с операциями поиска и обработки;
- поддерживает эффективную индексацию;
- может менять порядок ключей и не сохраняет форматирование исходного JSON.

Пример:

Можно создать GIN-индекс:

```
CREATE INDEX idx_users_data
ON users USING GIN (data);
```

### Что выбрать

**JSON** — когда важно сохранить исходное представление JSON и редко выполняются операции поиска внутри него.

**JSONB** — чаще предпочтительный вариант, когда JSON активно фильтруется, ищется и индексируется.

> В большинстве прикладных сценариев PostgreSQL рекомендуют использовать **JSONB**, если нет конкретной причины использовать `JSON`.

---

### Оконные функции

**Оконная функция** выполняет вычисление по набору связанных строк, но **не объединяет строки в одну**, в отличие от `GROUP BY`.

Общий вид:

```
function(...) OVER (
    PARTITION BY ...
    ORDER BY ...
)
```

Основные:

- `ROW_NUMBER()`;
- `RANK()`;
- `DENSE_RANK()`;
- `LAG()`;
- `LEAD()`;
- `SUM() OVER`;
- `AVG() OVER`.

### PARTITION BY

Разбивает строки на логические группы.

```
SELECT
    customer_id,
    amount,
    SUM(amount) OVER (
        PARTITION BY customer_id
    ) AS total_amount
FROM orders;
```

Каждая строка сохраняется, но получает сумму всех заказов своего клиента.

### ORDER BY

Позволяет учитывать порядок строк.

Например, получить предыдущую операцию:

```
SELECT
    customer_id,
    created_at,
    amount,
    LAG(amount) OVER (
        PARTITION BY customer_id
        ORDER BY created_at
    ) AS previous_amount
FROM orders;
```

### Пример ранжирования

```
SELECT
    employee,
    salary,
    RANK() OVER (
        ORDER BY salary DESC
    ) AS salary_rank
FROM employees;
```

Получаем рейтинг сотрудников по зарплате, при этом исходные строки сохраняются.

> **GROUP BY** → группирует и уменьшает количество строк.  
> **Window function** → сохраняет исходные строки и добавляет вычисленный результат.


# 🔴 Тема: Oracle 🔴

## 🥉На двойку: Как работает Oracle DB**

**Oracle Database** — реляционная СУБД от Oracle, предназначенная для хранения и обработки данных, работы с транзакциями и большими корпоративными системами.

**Основная схема работы:**

```text
Клиент / приложение
        ↓
Oracle Server
        ↓
SQL / PL/SQL
        ↓
Обработка запроса
        ↓
Buffer Cache / SGA
        ↓
Data Files
````

**Основные компоненты:**

- **Instance** — память + фоновые процессы, которые обслуживают БД.
- **Database** — физические файлы с данными.
- **SGA** — общая область памяти Oracle instance.
- **PGA** — память конкретного серверного процесса.
- **Data Files** — физическое хранение данных.
- **Control Files** — информация о структуре БД и состоянии файлов.
- **Redo Log** — журнал изменений для восстановления после сбоев.

**При выполнении SQL:**

1. Клиент отправляет SQL-запрос.
2. Oracle разбирает и проверяет запрос.
3. Определяет план выполнения.
4. Ищет необходимые данные в памяти или читает их с диска.
5. Выполняет операции.
6. Возвращает результат клиенту.

**Транзакции:**

- изменения выполняются в рамках транзакции;
- `COMMIT` фиксирует изменения;
- `ROLLBACK` отменяет изменения;
- используется механизм **Redo / Undo** для обеспечения надёжности и согласованности.

> Важная особенность Oracle — разделение **Database (физические файлы)** и **Instance (память + процессы)**.

---

## 🧐 **на тройку: Плюсы и минусы Oracle DB**

### Плюсы

- высокая производительность;
- хорошо работает с большими объёмами данных;
- развитая поддержка транзакций;
- высокая отказоустойчивость;
- развитые механизмы резервирования и восстановления;
- масштабируемость;
- развитые средства безопасности;
- мощный PL/SQL;
- широкий набор корпоративных возможностей;
- развитые инструменты мониторинга и администрирования.

### Минусы

- высокая стоимость лицензирования;
- сложнее администрирование по сравнению с более простыми СУБД;
- высокие требования к квалификации специалистов;
- сложнее миграция на/с Oracle;
- многие возможности специфичны для Oracle → возникает vendor lock-in;
- может требовать значительных ресурсов инфраструктуры.

> Oracle обычно выбирают для крупных критичных систем, где важны производительность, надёжность, транзакционность и корпоративные возможности.

## 😎 **на четверку: Ключевые особенности PL/SQL. Обработка NULL-значений**

### PL/SQL

**PL/SQL (Procedural Language/SQL)** — процедурное расширение SQL в Oracle.

Позволяет объединять SQL с программной логикой непосредственно внутри БД.

**Основные возможности:**

- переменные и константы;
- условия `IF / ELSE`;
- циклы `LOOP / FOR / WHILE`;
- процедуры;
- функции;
- курсоры;
- обработка исключений;
- триггеры;
- пакеты;
- работа с SQL внутри процедурного кода.

Пример:

```
DECLARE
    v_balance NUMBER;
BEGIN
    SELECT balance
    INTO v_balance
    FROM accounts
    WHERE id = 1;

    IF v_balance > 0 THEN
        DBMS_OUTPUT.PUT_LINE('Баланс положительный');
    END IF;
END;
/
```

### Зачем нужен PL/SQL

- выполнять бизнес-логику непосредственно в БД;
- уменьшить количество сетевых вызовов между приложением и БД;
- выполнять сложные последовательности операций;
- создавать процедуры и функции;
- централизовать часть логики на уровне БД.

---

### Обработка NULL

**`NULL`** означает отсутствие значения / неизвестное значение.

Важно:

> `NULL` — это **не `0`**, не пустая строка и не `FALSE`.

Нельзя проверять:

```
WHERE value = NULL
```

Правильно:

```
WHERE value IS NULL
```

или:

```
WHERE value IS NOT NULL
```

### NULL в вычислениях

Большинство арифметических операций с `NULL` дают `NULL`:

```
100 + NULL = NULL
```

Для подстановки значения используется `NVL`:

```
SELECT NVL(balance, 0)
FROM accounts;
```

Если `balance = NULL` → получим `0`.

Также используется `COALESCE`:

```
SELECT COALESCE(balance, 0)
FROM accounts;
```

`COALESCE` возвращает первое значение, которое не является `NULL`.

### NULL и сравнения

```
NULL = NULL       → UNKNOWN
NULL <> NULL      → UNKNOWN
NULL > 10         → UNKNOWN
```

SQL использует **трёхзначную логику**:

- `TRUE`;
- `FALSE`;
- `UNKNOWN`.

Поэтому для проверки `NULL` используются именно:

```
IS NULL
IS NOT NULL
```

### NULL в PL/SQL

В PL/SQL для проверки:

```
IF v_value IS NULL THEN
    ...
END IF;
```

Для обработки `NULL` часто используются:

```
NVL()
COALESCE()
NULLIF()
```

**Особенность Oracle:**

В Oracle пустая строка `''` в большинстве строковых типов рассматривается как `NULL`.

> На интервью важно не путать `NULL` с пустым значением: `NULL` означает отсутствие/неизвестность значения, а не конкретное значение.


# 🔴 Тема: Хранилища и манипуляция данными 🔴

## 🥉На двойку: Что такое Data Warehouse? Какие основные задачи решает DWH в бизнесе? В чем отличие DWH от Data Lake?**

**Data Warehouse (DWH)** — централизованное хранилище структурированных данных из различных источников, предназначенное прежде всего для аналитики и принятия бизнес-решений.

**Основные задачи DWH:**
- сбор данных из разных систем;
- хранение исторических данных;
- объединение и консолидация данных;
- аналитика и построение отчётности;
- расчёт KPI;
- поддержка принятия бизнес-решений;
- подготовка данных для BI.

> DWH — **аналитическое хранилище**, а не основная БД приложения.

### DWH vs Data Lake

**DWH:**
- структурированные и подготовленные данные;
- заранее определённая схема;
- данные очищены и преобразованы;
- используется в основном для BI и аналитики.

**Data Lake:**
- хранит сырые данные;
- может хранить структурированные, полуструктурированные и неструктурированные данные;
- схема может определяться при чтении;
- подходит для Big Data, ML, исследований и последующей обработки.

> **DWH — сначала структура → потом данные.**  
> **Data Lake — сначала данные → структура определяется при использовании.**

---

## 🧐 **на тройку: Объясните концепцию ETL/ELT процессов. В чем их отличие? Что такое витрина данных (Data Mart)? Для чего она нужна?**

### ETL

**ETL (Extract → Transform → Load)** — данные сначала извлекаются, затем преобразуются и после этого загружаются в DWH.

```text
Source
  ↓
Extract
  ↓
Transform
  ↓
Load
  ↓
DWH
````

**Extract** — получение данных из источников.

**Transform** — очистка, преобразование, объединение, расчёт показателей.

**Load** — загрузка подготовленных данных в DWH.

### ELT

**ELT (Extract → Load → Transform)** — данные сначала загружаются в хранилище, а преобразование выполняется уже внутри DWH.

```
Source
  ↓
Extract
  ↓
Load
  ↓
DWH
  ↓
Transform
```

### ETL vs ELT

**ETL:**

- преобразование до загрузки;
- в DWH попадают уже обработанные данные;
- меньше требований к самому DWH.

**ELT:**

- сначала сохраняем данные;
- трансформации выполняются внутри DWH;
- удобно для современных мощных облачных DWH;
- проще сохранять исходные данные.

> Главное отличие: **где выполняется Transform — до загрузки или после.**

---

### Data Mart

**Data Mart (витрина данных)** — специализированная часть DWH, содержащая данные для конкретного направления бизнеса, команды или задачи.

Например:

```
DWH
 ├── Sales Data Mart
 ├── Finance Data Mart
 ├── Marketing Data Mart
 └── Customer Data Mart
```

**Зачем нужна:**

- упростить работу аналитиков;
- предоставить данные в удобной структуре;
- ускорить аналитические запросы;
- ограничить набор данных конкретной предметной областью;
- упростить построение BI-отчётов.

> **DWH — единое большое хранилище. Data Mart — специализированная витрина внутри/на основе DWH.**

---

## 😎 **на четверку: В чем отличие OLAP от OLTP? Какая из этих методик используется в DWH? Назови инструменты BI для визуализации данных из DWH**

### OLTP

**OLTP (Online Transaction Processing)** — обработка большого количества коротких транзакционных операций в реальном времени.

Характерно:

- `INSERT / UPDATE / DELETE`;
- большое количество пользователей;
- быстрые короткие транзакции;
- высокая целостность данных;
- обычно нормализованная структура.

**Примеры:**

- банковские операции;
- оформление заказа;
- создание пользователя;
- проведение платежа.

---

### OLAP

**OLAP (Online Analytical Processing)** — аналитическая обработка больших объёмов данных.

Характерно:

- сложные `SELECT`;
- агрегации;
- `GROUP BY`;
- анализ исторических данных;
- построение отчётов;
- небольшое количество, но тяжёлых запросов.

**Примеры:**

- продажи за несколько лет;
- анализ выручки;
- динамика KPI;
- сегментация клиентов.

### OLTP vs OLAP

| Критерий | OLTP | OLAP |
|---|---|---|
| Назначение | Операционная работа | Аналитика |
| Запросы | Короткие | Сложные |
| Данные | Текущие | Исторические |
| Операции | INSERT / UPDATE / DELETE | В основном SELECT |
| Структура | Нормализованная | Часто денормализованная |
| Нагрузка | Много небольших запросов | Меньше тяжёлых запросов |

**DWH используется для OLAP.**

Типичная архитектура:

```
OLTP-системы
     ↓
   ETL/ELT
     ↓
    DWH
     ↓
   OLAP
     ↓
BI / отчёты / аналитика
```

---

### BI-инструменты

**BI (Business Intelligence)** — инструменты для анализа данных и визуализации бизнес-показателей.

Примеры:

- **Power BI**;
- **Tableau**;
- **Qlik Sense**;
- **Looker / Looker Studio**;
- **Apache Superset**;
- **Metabase**.

Используются для:

- dashboards;
- графиков;
- отчётов;
- KPI;
- фильтрации и drill-down;
- анализа данных из DWH.

> Связка: **DWH хранит и подготавливает данные → BI визуализирует их для пользователя.**
